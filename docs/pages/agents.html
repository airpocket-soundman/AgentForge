5. エージェント構成

オーケストレーターは“現場監督”。コードは書かず、判断・分解・委任・統合に徹します。実装は専門ワーカーが担当します。

常駐エージェント（core-api）

エージェント責務モデル
Receptionユーザー即応、進捗説明、中止・変更・承認の受付、取り次ぎ軽量 Gemini ＋ 定型
Orchestrator要求理解、タスク分解、API/UI 要否判断、ワーカー選定、作業計画生成、結果統合Gemini（判断時）
Orchestrator が作るのはコードではなく作業命令書（JSON）。「誰が・何を・どの順で」を決め、Control Plane に申請する。

専門ワーカー（機能を“作る”・ビルド時／必要時起動）

下記は機能を作るための汎用ワーカー。機能ごとに新規作成せず再利用する。完成後は停止。

ワーカー役割出力
UI Designer画面構成・情報設計view_manifest.json
API DesignerAPI 仕様・データ構造設計api_spec
ProgrammerAPI / UI 実装、テスト生成source bundle
Test軽量検証test result
DevOpsCloud Build 起動申請、ログ要約、Rollback 候補提示deploy plan
Review / Safety差分の危険度評価、権限・秘密参照検査review report

役割分担の原則

  • Orchestrator は自分でデプロイしない・IAM を触らない・Secret を読まない
  • ワーカーは非常駐。呼ばれた時だけ起動し、必要な文脈だけを受け取って結果を書き戻す
  • ワーカーは自分の権限を増やせない・別ワーカーを勝手に作れない
  • 副作用操作はすべて Tool Gateway 経由、出力はスキーマ検証

生成機能の実行モデル（“生きた機能”）

生成された機能は静的なフォームではない。骨格は決定的な API、入出力の境界では小型 LLM が自然言語を扱い、UI も自然言語で作り替えられる。動いていない間は停止（非常駐）。

図 5-1. 生成機能の三点セット＝境界 LLM（小型）＋決定的 API ＋動的 UI。文脈は Context DB に永続化。

編集可能な UI 要素（チェックボックス・メモ欄など）は、すべて対応する永続化 APIに紐づく。機能を追加・拡張するたびに、これらの API を機能ごとに設計・生成・登録していく（詳細は「データ設計」章を参照）。

コンテキストの永続化

ワーカーは短命なので、文脈をワーカー内に持たせない。Firestore（Context DB）に保存し、起動のたびに最小限を読み直す（rehydrate）ことで、非常駐でも継続性を持たせる。

保存先中身
context_chunks（＋Vector Search）文脈・判断ログ・ユーザー設定・好み
worker_registry / worker_definitionsワーカー定義（目的・許可ツール・I/O スキーマ）
worker_runs各実行の入出力・要約・トークン
conversations機能ごとの対話状態
Cloud Storage大きな生成物・添付（参照だけ Firestore に）

ワーカーには毎回 context_refs（最小ポインタ）だけ渡し、本体は Firestore から取得する。

API化 か ワーカー化 かは Orchestrator が判断

「この要求は新しい API で足りるのか／LLM ワーカーが要るのか」を Orchestrator が判断する。決め打ち自動化にはできないこの判断こそ、“AI エージェントである必然性”（審査基準1）の見せ場。
処理の性質選択
安定・反復・決定的（保存/一覧/完了/並び替え）API 化（LLM 不使用）
自然言語の理解・整理・任意出力境界 LLM（小型・必要時）
継続的な判断が要る（要約・推薦）専用ワーカー（非常駐・Context DB 連携）

ADK の使いどころ

Orchestrator とワーカーを ADK（Agents Development Kit）で構成し、Gemini の function calling / structured output で作業計画・UI 仕様・API 仕様を JSON 化します。これが必須要件「Google Cloud AI 技術の利用」を満たす中核です。

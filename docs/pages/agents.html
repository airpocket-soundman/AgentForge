5. エージェント構成

名前・役割・運用ルールの正本は 5b. ワーカー定義・運用ルール、 Reviewer の判定基準は 5c. コード規約。本ページは現行構成の概観です。

5 種の AI ワーカーが MCP 的プロトコル（request/report・task_id 相関）で協業。 公式名は英語。すべて非常駐（不要時は休止・コンテキストは Firestore に永続化して rehydrate）。

ワーカー一覧（現行）

ワーカー責務モデル（能力帯）
Receptor メインチャットの受付。曖昧な依頼を質問で具体化→復唱→「お願い」で取り次ぎ。可否質問は自分で回答。 パイプラインの停滞を無音時間で自発監視し ①停止/②待つ/③再トライ を提示（2回で強制停止）。 FLASH
Orchestrator 制作・改変パイプラインの統括。設計案（受け入れ条件つき）、コード生成（完結HTML＋操作ツール）、 改変は差分パッチ優先、Tester/Reviewer への委任、プレビューのデプロイ。失敗は自動リトライ。 分類・計画＝FLASH／コード生成＝PRO
Tester 生成物を本番相当エミュレータ前提で検証。承認済み受け入れ条件を1つずつ ✅/❌＋致命的な動作不能を判定。NG は差し戻し。 FLASH
Reviewer コード規約（5c）への適合＋設計・ユーザーニーズへの適合（設計案との一致・要求台帳を壊していないか）を判定。判定のみ（書き換えない）。 FLASH
Specialist Worker 各ミニアプリ専属。アプリチャット経由で中身（データ・表示）を操作（宣言済み MCP 形式ツールのみ）。 構造変更の依頼はメインチャットへ自動取り次ぎ。 FLASH
モデルは能力帯で本番と開発を揃える：FLASH＝Gemini Flash↔Claude Haiku／PRO＝Gemini Pro↔Claude Opus。 開発・デモは claude CLI ブリッジ（コスト節約）、本番は Gemini API。使用中モデルはステータスモニターに表示。

役割分担の原則（権限境界）

  • ワーカーは自分の権限を増やせない・別ワーカーを勝手に作れない。
  • AI は生成物を pending 登録するのみ。公開・巻き戻しは人間の承認（Control Plane）。未完成（stub）は公開拒否。
  • Reviewer / Tester は判定のみ。Specialist Worker は担当ミニアプリ内に限定。
  • ミニアプリは iframe サンドボックス（外部通信・localStorage 遮断、保存は AF.load/save のみ）。

生成ミニアプリの実行モデル

ミニアプリ＝AI が書いた単一の完結 HTML アプリ（kind=app）。サンドボックス iframe で実行され、 シェルが注入する小さなブリッジだけで外界と接続します。

接点内容
AF.load() / AF.save()状態の永続化（サーバ側・機能単位）。localStorage/ネットワークは使えない
commands＋applyAgentCommand(name,args)MCP 形式の操作ツール宣言。Specialist Worker が自然言語→ツール呼び出しに変換して中身を編集
AF.setChatContext(id,label)複数画面・詳細画面などの文脈ごとに Specialist Worker の会話履歴を分割
AF.setChatVisible(true/false)画面単位で下部アプリチャットの表示/非表示を制御（ワーカーは付いたまま）

PC/スマホ両対応（viewport＋可変レイアウト）と「HTML 内にチャット UI を作らない」が規約（5c）。

コンテキストの永続化（非常駐の支え）

保存先（Firestore）中身
conversations会話・フロー段階・ビルド状態（ハートビート）
workers / worker_messages / worker_contextsワーカー状態（モデル・待機理由）／MCP的 request-report ログ／rehydrate 用コンテキスト
feature_versions / feature_requirements公開ごとの版スナップショット／要求台帳（改変で過去要求を壊さない）

“API化 か ワーカー化 か”は Orchestrator が判断

安定・決定的な操作（保存/一覧/巻き戻し等）は決定的 API・LLM 不使用に、自然言語の理解・整理は 境界の小型 LLM（Specialist）に、設計・生成のような重い判断は PRO に。 この振り分けの判断こそ「AI エージェントである必然性」（審査基準1）の見せ場。

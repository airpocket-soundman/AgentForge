3. システム構成図

このページは初期構想（参考資料）。 ワーカー・パイプライン・承認フロー・安全装置の 正本は 5b. ワーカー定義・運用ルール／5c. コード規約（到達点はリポジトリ直下の VISION.md）。 記述が食い違う場合は正本に従ってください。

フロントは Firebase Hosting、ロジックは Cloud Run、状態は Firestore。AI には強権限を渡さず、デプロイ操作は Tool Gateway に集約します。

図 3-1. 全体構成。AI は判断・計画・申請を担当し、Cloud 操作は Control Plane / Tool Gateway 経由に限定。

デプロイ単位（ソロ向けに最小化）

単位中身備考
agentforge-webFirebase Hosting（Web Shell）静的配信
agentforge-core-apiReception / Orchestrator / Control Plane / Tool Gateway論理分離・1サービス同居
agentforge-workerWorker Runner（UI/API/Programmer…）Cloud Tasks から起動

※ 論理的には仕様書通りエージェント/層を分離（実運用への配慮）しつつ、デプロイは 2 サービスに集約して運用負荷を下げています。

通信とコスト（scale-to-zero）

ブラウザと Reception の接続は REST/HTTPS（Firebase Auth の ID token）。MCP は使いません（MCP はエージェント↔ツール用で、常駐接続は scale-to-zero と相性が悪いため）。進捗・状態のライブ更新は、ブラウザが Firestore をリアルタイム購読するのでバックエンドを起こし続ける必要がありません。

図 3-2. 通信とコスト。操作は REST、ライブ更新は Firestore 購読。エージェントは非常駐で、アイドル時はほぼ ¥0。
要素アイドル時課金
core-api / worker（Cloud Run, min=0）0 インスタンスリクエスト処理中だけ
Gemini呼ばない呼んだ時だけ（小型は無料枠中心）
Firestore / Storage / Hosting保存のみ実質ゼロ

※ 原則すべて min=0（コールドスタート許容）でコスト最優先。初回リクエストのみ数秒の起動待ちが出るが、デモ前にウォームアップ要求を 1 回投げれば回避できる。常駐（min=1）は採用しない。

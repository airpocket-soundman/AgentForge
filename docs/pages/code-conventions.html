コード規約（Reviewer 判定基準）

Reviewer がデプロイ前に適合を判定する基準です。主対象は Orchestrator が生成する ミニアプリのコード（HTML / API / 操作ツール）。末尾にリポジトリ本体（Python/TS）の開発規約も併記します。

この規約は、実行時にワーカーへ注入される backend/app/agents/policy.md / ui_designer.md と同一の規範です。差異が出たら本ページを正とし、 両者を一致させてください。ワーカー定義（workers.html） の Reviewer から参照されます。
静的な規約適合は Reviewer、動的な「実際に動くか」の検証は Tester（workers.html）が担当します。 本ページは主に Reviewer の判定基準（静的規約）。Tester は生成物を実行して起動・主要操作・エラー有無・要求充足を確かめます。

1. 生成物の形式

  • アプリ型（kind=app）は単一の完結した HTML。出力は JSON のみ （feature / title / description / theme / html / commands）。前後の説明やコードフェンスを付けない。
  • html は <!DOCTYPE html> から始まり、構造タグ＋閉じタグを持つ実体であること。 謝罪文・説明文・空文字を html に入れない（公開対象は「動くアプリ」）。

2. 自己完結・サンドボックス

  • <style> と <script> を内包し、外部 CDN・外部通信なしで単体動作する。
  • 使用禁止：localStorage / cookie / fetch / 外部通信 / 別ウィンドウ。
  • 外部サービス連携は、生成 HTML から直接通信せず、ミニアプリがユーザー入力から AF.defineConnector({...}) で feature-scoped connector を定義し、登録済み action を AF.api("connector_id.action_id", params) で呼ぶ。URL・ヘッダ・トークンは AgentForge backend が管理し、生成 HTML の state には保存しない。
  • 状態保存はAF.load() / AF.save() のみ（サーバ側にミニアプリ単位で永続化）。 画面遷移・リロード・別メニューへ移動して戻った後も途中状態を復元するのがミニアプリの基本仕様。 タスク／メモ／フォーム／設定だけでなく、ゲームの盤面・スコア・進行状態も保存対象。 保存が不要なのは、電卓・時計など途中状態を保持しなくても機能価値が落ちない一時操作に限る。

3. 操作ツール契約（MCP 形式・必須）

  • HTML 内に window.applyAgentCommand = function(name, args){ ... } を実装。 name に応じて中身（描画・テキスト・データ等）を実際に変更し、必要なら AF.save を呼ぶ。 未知の name は無視（安全側）。
  • 変更可能な主要プロパティを網羅的にツール化する（ユーザーが言いそうな操作を広めに）。
  • 公開した操作を commands（[{name, description, inputSchema}]）に列挙。 name は applyAgentCommand と一致、inputSchema は引数の JSON Schema。
  • 自然言語の想定から逆算して API を設計する。作成/追加だけでなく、更新/変更、 削除/消去、一括操作、対象指定、メモ追記、設定変更、初期化/クリア、Undo など、そのアプリで ユーザーが言いそうな依頼を具体的に想定してツール化する。
  • データ中心アプリは state 直接編集をパイプラインに含める。予定、タスク、メモ、在庫、 家計簿、日記、CRM、台帳、フォーム等は、commands だけに閉じ込めず、 worker_state_mode を state または hybrid にし、 state_schema に AF.save() する状態構造を具体的に宣言する。 Specialist Worker は現在の state を schema に沿って直接編集でき、未知の新アプリにも対応できる。
  • hybrid は、データ更新は state 直接編集、UI操作や即時表示操作は commands を併用する方式。 お絵描き・ゲーム・電卓のように UI 操作 API が自然なものは commands を選んでよい。
  • 生成 manifest には worker_instructions と worker_examples を含め、 Specialist Worker が役割・利用可能 API・state_schema の編集方針・自然言語から操作への対応・曖昧な場合の聞き返し方を アプリごとに理解できるようにする。
  • 生成 manifest には worker_eval_cases、clarification_policy、dangerous_action_policy も含める。 追加/更新/削除/一括操作/曖昧な対象/異常値/担当外の構造変更など、Specialist Worker が誤りやすい自然言語指示を アプリごとに具体的に想定し、Tester が検証できる材料にする。
  • 純粋表示のみのアプリは commands を空配列にしてよい。

4. UI / UX

  • body は margin:0 でビューポートいっぱいに広げ、モダンで見やすく、ボタンは押しやすく。
  • 入力はマウスとタッチの両対応（pointer イベント推奨）。
  • 大きいファイルは AF.saveBlob/loadBlob/listBlobs/deleteBlob（端末内・IndexedDB）に保存。 AF.save の状態（約1MB上限）に巨大 base64 を入れない（保存失敗→リロードで消える）。状態にはメタ/抽出テキストのみ。 Blob は端末ローカルのため loadBlob が null の場合の欠落表示を用意する。
  • PC とスマホの両対応（レスポンシブ）：<meta name="viewport"> を入れ、固定幅にせず flex/grid・% で画面幅に追従。必要なら @media（目安 600px）でスマホ向けに最適化し、 縦持ちスマホでも操作できること。
  • 見た目はテーマで一貫させる：default / warm / forest / ocean の4種のみ。 ユーザー指示が曖昧なら内容に最も近いもの、指定が無ければ default。独自テーマ（生CSSの作り込み）で統一感を壊さない。

5. 機能の忠実性

  • ユーザーが求めた機能を省略せず「実際に動く形で」実装する。 フォーム＋一覧で代替したり、機能を削ったりしない。
  • 例：「お絵描き」→ 実際に描ける（ペン/消しゴム/色/太さ/Undo/全消去 等）。「電卓」→ 実際に計算できる。 「タスク管理」→ 追加・完了・削除ができ保存される。「〇×ゲーム」→ 実際に遊べ、盤面・手番・結果が保存される。

6. 命名・テーマ

  • feature スラッグは英小文字（[a-z0-9_]）。例：paint / calculator / task_manager。
  • theme は前述の4種のみ。

7. ワーカー標準（生成 view）と画面レイアウトの分離

アプリ表示エリア（上部＝生成 HTML）とアプリチャット（下部）は分離する。 has_worker=true はシェルが画面下部にアプリチャット用パネルを用意する意味であり、 生成 HTML 自身にチャット／メッセージ入力／AI アシスタント欄を作ってはいけない （作ると上部アプリ内と下部パネルでチャットが二重になる）。生成 HTML はアプリの中身だけ。
  • 機能には機能 AI ワーカー（Specialist Worker）を既定で付ける（has_worker=true＝アプリに 1 つが標準）。 ユーザーが「ワーカー不要」等を明示した場合のみ false。チャット UI は下部パネルが担い、生成 HTML には含めない。
  • アプリチャットは受付即時応答を標準にする：ユーザーが Specialist Worker に送信した直後、シェルは 「ワーカーが内容を確認して作業に入っている」旨の短い仮メッセージを表示し、完了時に実際の返答・操作報告を追記する。 生成 HTML 自身にこの受付表示やチャット UI を作ってはいけない。
  • アプリチャットのコンテキスト分割：複数画面・タブ・詳細画面など、1つのアプリ内に複数の作業文脈がある場合は、 画面遷移時に AF.setChatContext("screen-or-object-id", "表示名") を呼ぶ。会話履歴はアプリごと、さらに context ごとに分割保存される。 単一画面アプリは既定の default コンテキストでよい。
  • 画面ごとのチャット欄の表示/非表示：ユーザーが画面単位の指定をした場合、生成 HTML は その画面への遷移時に AF.setChatVisible(false/true) を呼んで下部パネルを出し入れする （ワーカーは付いたまま・パネルの表示だけが変わる）。指定が無ければ呼ばない（既定=表示）。
  • 状態を持つ要素（チェック／メモ／フォーム／設定／ゲーム進行／スコア／盤面）は対応する永続化 API にバインドする。
  • ミニアプリ自体の作成・構造変更はメインチャット専任。Specialist Worker は中身の編集のみ（担当外の構造変更をしない）。構造変更を頼まれたら検知してメインチャット（Receptor → Orchestrator）へ取り次ぐ。

8. 安全・権限（生成時）

  • AI は生成物を pending 登録するのみ。active 化・本番反映・rollback は人間の承認を要する （Control Plane 経由・全操作を監査）。
  • パイプラインの判断・進捗・成果物・Tester/Reviewer 結果は Agent Harness の pipeline_runs に記録する。ユーザーには raw trace ではなく、短い進捗・判断理由・承認前サマリーとして表示する。
  • 副作用操作はすべて Tool Gateway 経由、出力はスキーマ検証。
  • 安定・決定的な操作は API 化（CRUD 等・LLM 不使用）。自然言語での運用・整理・設定変更は Specialist Worker に委ねる （境界 LLM ＋ 決定的 API ＋ 動的 UI）。

9. 生成 API / データ規約

パス・メソッド・副作用レベル

  • パスは /api/app/<feature>/<resource> の形（feature スラッグで名前空間化）。api_id は snake_case。
  • 各 API は method・side_effect_level を宣言する（承認・監査の粒度に使う）。
メソッド用途side_effect_level
GET一覧・取得read
POST作成low（外部呼び出し・課金を伴うなら medium/high）
PATCH / PUT更新low
DELETE削除medium

データ分離

  • データはミニアプリ単位でスコープ（feature で名前空間化）。他ミニアプリのデータに触れない。
  • サーバ側保存はミニアプリ単位（HTML アプリは AF.load/save、API 型は feature 付きのコレクション）。
  • アプリ削除時は削除方法を確認する。ユーザーがアプリ自体の削除を明示した場合、 「巻き戻し可能な状態で削除」か「完全に削除」かを選ばせる。 巻き戻し可能な削除では左メニューから外すだけで、データ・版履歴・要求台帳などは残す。 完全削除では生成ビュー、AF.save の state、エンティティ、アプリチャット履歴、版スナップショット、 要求台帳、feature_states の該当メタ情報などを削除する。 AF.saveBlob で現在の端末に保存した Blob も、完全削除を行ったブラウザでは同時に削除する。 監査ログは削除操作の証跡として残す。巻き戻し（rollback）は削除ではなく、復元可能性を保つためデータを消さない。

入出力フォーマット

  • JSON。キーは snake_case。一覧は { "items": [...], "next": <cursor|null> }。
  • エラーは適切な HTTP ステータス＋ { "error": { "code", "message" } }。サーバは入力をスキーマ検証する。

10. リポジトリ本体の開発規約（Python / TS）

  • Python：from __future__ import annotations・型注釈・モジュール docstring を付ける。 router（HTTP）と service（ロジック）を分離。データは pydantic モデル。
  • LLM 到達不可・解析失敗時は必ず決定的フォールバックでパイプラインを止めない （広域 except は // noqa: BLE001 を付し、握りつぶしでなくフォールバックに繋ぐ）。
  • ワーカーの公式名は英語（Receptor / Orchestrator / Reviewer / Specialist Worker）。
  • テストは Docker 上の pytest（手順はリポジトリ直下の ENVIRONMENT.md §2(C)）。

11. Reviewer チェックリスト

Reviewer は各項目を判定し、1つでも不適合があれば needs_revision を返す（指摘は findings に列挙）。

誤検知しないこと： has_worker は生成物 JSON（マニフェスト）のフィールドではない （パイプラインが view 登録時に付与する別フラグ）。「生成物に has_worker が無い」「チャット欄が無い」を 規約違反として指摘しない。チャットは下部の別パネルがシェルから提供され、生成 HTML には含めないのが正。
#判定項目不適合の例
1出力が規定 JSON・html が実体の完結 HTMLコードフェンス付き／説明文が html に混入
2外部通信なしで自己完結・サンドボックス禁止 API 不使用fetch/外部CDN/localStorage 使用（外部接続は AF.defineConnector と AF.api のみ可）
3状態を持つアプリは AF.load/save でサーバ保存・復元localStorage に保存している／ゲームの盤面・スコアが画面遷移で消える
4applyAgentCommand 実装＋commands 整合、または worker_state_mode＋state_schema による state 直接編集設計。専門ワーカー向け指示も必須ツール未実装／commands と名前不一致／データ中心アプリなのに state_schema が無い／worker_instructions が無く自然言語運用の想定が薄い
4b専門ワーカー評価ケースと安全方針worker_eval_cases が無い／異常値や一括削除の聞き返し方針が無い
5要求機能を実際に動く形で実装（代替・省略なし）「お絵描き」がフォーム＋一覧になっている
6テーマは4種のみ・feature は英小文字独自テーマ／スラッグに日本語
7マウス／タッチ両対応・body margin:0・PC/スマホ両対応（viewport メタ＋可変レイアウト）タッチで操作不能／固定幅でスマホで崩れる・viewport メタなし
8生成 HTML 内にチャット／メッセージ入力／AI アシスタント UI を含まない（アプリチャットは下部の別パネル）html にチャット欄・送信ボタン付き入力欄・「アシスタント」等の会話 UI が入っている
9生成 API の side_effect_level が適切更新系を read 宣言

ワーカー定義と運用ルール（正本）

このアプリでは、複数の異なるコンテキストを持つ LLM セッションが協業します。 本ドキュメントは、その各セッション（=ワーカー）の名前・役割・運用ルールを定める唯一の正本です。 実装はこの定義に一致させ、変更が必要な場合は先にここを更新します。

このページは CLAUDE.md から「開発セッション必読」として参照されています。 ワーカーやミニアプリ生成パイプラインのコードを触る前に、必ず本ページの定義に従ってください。
公式名称は英語表記。 全ワーカー種別の正式名は英語とし、日本語は読み・補助とします （Receptor / Orchestrator / Reviewer / Specialist Worker）。

1. 基本概念

Worker（ワーカー）

異なるコンテキストを持つ LLM セッションを「ワーカー」と呼びます。 ワーカー同士は独立して動作しますが、定められたルールに基づいて 別のワーカーから指示を受け、報告を返します。

メインチャット（Main Chat）

このアプリの中心となる機能です。ユーザーはここでアプリと対話します。

Receptor（レセプター）

メインチャットの受付をするワーカーです。 メインチャットでチャット（会話）を行うのは、この Receptor です。

ミニアプリ（Mini-App）

このアプリの特徴である、自由に追加・改変できる機能を「ミニアプリ」と呼びます。

Specialist Worker（専門ワーカー）

個々のミニアプリ向けに設定されたワーカーです。そのミニアプリを扱うことができます。

Orchestrator（オーケストレーター）

ミニアプリの制作・改変作業のパイプラインには複数のワーカーが携わります。 これを統括するワーカーが Orchestrator です。

Reviewer（レビュワー）

Orchestrator の作ったコードをレビューするワーカーです。 主に、このアプリの中で定めたコード規約に適合しているかを判定します。

Tester（テスター／検証ワーカー）

Orchestrator の作ったコードを実際に動かして検証するワーカーです。 コード規約の適合（Reviewer）とは別に、「ちゃんと動くか・要求どおりか」を確かめます。 検証は Docker 内に用意した「本番相当エミュレータ」環境（Firestore エミュレータ＋backend ＝ docker-compose.dev 相当）で行う。LLM プロバイダのみ claude に差し替え（コスト節約）、 それ以外は本番同等で実働させ、本番デプロイ前に本番同等条件で動作確認する。

2. ワーカー一覧

ワーカー（公式名）役割運用ルール
Receptor
レセプター		 メインチャットの受付。ユーザーとの会話を担当し、曖昧な依頼は質問で具体化し、依頼内容を復唱してユーザーの確認（「お願い」）を得てから Orchestrator に取り次ぐ。可否質問・相談は自分で答える（投げない）。実行中パイプラインの進捗を監視し、タイムアウトを判定してユーザーに停止可否を確認する。 メインチャットで会話するのは Receptor のみ。軽い処理のみを受け持ち即応する。
Orchestrator
オーケストレーター		 ミニアプリ制作・改変パイプラインの統括。設計・改変計画の立案、コード作成（HTML作成・API作成・Specialist Worker の設定）、Tester／Reviewer への検証・レビュー依頼、プレビューのデプロイを行う。作業の合間に進捗（開始・失敗・リトライ）を Receptor へ随時報告する。 ユーザー（プロジェクト）単位で最大 3 つまで同時稼働（複数タスクの同時進行のため）。
Reviewer
レビュワー		 Orchestrator が作ったコードをレビューし、問題があれば指摘してやり直しを命じる。主にコード規約への適合を判定。 Orchestrator はデプロイ前に必ずレビュー依頼する。
Tester
検証ワーカー		 Orchestrator が作ったコードを実際に動かして検証する（起動するか・主要な操作（commands）が動くか・コンソールエラーが無いか・要求どおりか）。動かなければ差し戻す。 Orchestrator はデプロイ前に必ず検証依頼する（Reviewer と並ぶゲート）。検証は本番相当の Docker エミュレータ（モデルのみ claude）で実行。
Specialist Worker
専門ワーカー		 個々のミニアプリの中身（データ・表示）を扱う。ミニアプリごとに設定される。担当外の構造変更（新機能・項目追加など）を頼まれたら検知し、メインチャットへ取り次ぐ。 Orchestrator がミニアプリ制作時に設定する。

3. ミニアプリ 制作・改変パイプライン

統括は Orchestrator。Receptor を起点に、設計 → 実行命令 → コード作成 → 検証（Tester）・レビュー（Reviewer） → デプロイ → 公開承認の順で進みます。

フロー図（アプリ制作・改変指示）

図 3-1. アプリ制作・改変フロー。設計案はユーザー承認（⑤）を経てコード化し、デプロイ前に Tester（動作検証）と Reviewer（規約適合）の両方を通す（どちらか NG なら⑥へ差し戻し）。⑩でプレビューをデプロイして Orchestrator は停止し、⑪のユーザー承認「反映して」で Control Plane が公開・有効化する。進捗・検証・レビュー状況は Receptor 経由でユーザーへ共有。停滞時のタイムアウトは Receptor が判定しユーザーが選択する。

Orchestrator の役割

  1. 指示の確認：Receptor を通じてユーザーの指示を確認する。
  2. 計画の立案：アプリの新規設計・改変の具体的な計画を立てて返す。 曖昧で判断できない要点があれば Receptor 経由でユーザーに確認してよい（過剰に聞かない。設計案の提示自体が確認を兼ねる）。
  3. 実行：Receptor からアプリ制作・改修の実行命令を受けて、実際にコードを作ってデプロイする。
    • アプリ制作には HTML 作成 / API 作成 / Specialist Worker の設定 などが含まれる。

進捗報告（Orchestrator → Receptor → ユーザー）

Orchestrator は、Receptor の指示を受けて設計やコーディングを行う合間に、可能な限り Receptor へ進捗を報告する。 Receptor はそれをユーザーへ報告する。これによりユーザーは「いま何が起きているか」をリアルタイムに把握できる。

  • 何を始めるか（例：設計開始、HTML 生成開始、API 作成開始、レビュー依頼）
  • 何を失敗したか（例：生成失敗、レビュー不適合）
  • 何をリトライしているか（例：指摘を反映して再生成中）
  • その他、節目ごとの状況

※ これらは作業途中の進捗報告（interim report）であり、作業完了時の最終報告（status=ok 等）とは別。報告経路はワーカー間プロトコル（§7）に従う。

検証・レビューのループ（デプロイ前）

  1. Orchestrator はデプロイ前に Tester に動作検証を、Reviewer に規約レビューを依頼する。
  2. Tester は本番相当の Docker エミュレータ（モデルのみ claude）で生成物を実際に動かし「動くか・要求どおりか」を、Reviewer はコード規約への適合を判定する。
  3. どちらかで問題があれば指摘し、Orchestrator にやり直しを命じる。
  4. Orchestrator はその結果を受けて再度コーディングを進める。
  5. 両方を通過したらプレビューとしてデプロイし、Orchestrator は停止する。
  • 受け入れ条件で検証する：設計案には動作で検証できる受け入れ条件（例「=を押すと計算結果が表示される」）を含め、 ユーザーは「これで作って」で条件ごと承認する。Tester は完成品を条件ごとに ✅/❌ で判定し、結果はチャットに明細表示される。
  • 生成失敗は自動リトライ：LLM 未到達等で生成が失敗（仮ページ）した場合、Orchestrator は 「⚠️ リトライ中」と可視化したうえで1回自動で再生成する（それでも失敗なら報告して停止）。

公開（有効化）の承認 ― 人間ゲート

デプロイはプレビュー（まだ本公開ではない）。ユーザーが「反映して」で承認すると、 Receptor 経由で Control Plane が公開・有効化する。この有効化に Orchestrator は不要（再起動しない）。

  • 人間の承認ゲートは3つ：①受付確認（Receptor が依頼内容を復唱→「お願い」）＝Orchestrator へ依頼、 ②設計承認（「これで作って」）＝コード化に進む、③公開承認（「反映して」）＝有効化する。
  • 承認しなければプレビューのまま。破棄も選べる。AI は勝手に本公開しない（安全側）。
  • プレビュー段階でも修正できる：「反映して」の前に修正指示を送れば、候補だけを再生成→再検証→再プレビューする （公開済み・本番には一切影響しない）。納得いくまで磨いてから「反映して」。
  • 公開のたびに、その版（HTML・設定のスナップショット）を保存する。これが「巻き戻し」（§8）で直前の版へ即時に戻す土台になる。
検証・レビューの可視化： 開始（Orchestrator → Tester／Reviewer の依頼）と 結果（動作検証の合否・規約の合否・指摘）は Receptor にも共有され、 Receptor からユーザーへ報告する。ユーザーは常に「いま検証／レビュー中か・何が問題か」を メインチャットで把握できる。

差し戻しループとタイムアウトの制御

2 種類の制御を分けて扱う。

(a) 品質ループ（Tester／Reviewer 差し戻し） ― 時間ではなく品質の繰り返し。

  • Tester が動作 NG、または Reviewer が規約不適合なら needs_revision を返し、Orchestrator が作り直す。
  • この繰り返し自体を自動回数で打ち切らない（止めるかどうかは下記タイムアウト制御＝ユーザー判断に委ねる）。

(b) タイムアウト／停滞の制御 ― 判定は Receptor、停止判断はユーザー。

  • タイムアウトで自動的に Orchestrator を止めない。 タイムアウト（＝想定時間を超えた・停滞している）は Receptor が判定する（Receptor はユーザー側の見張り役。監視はステータスを購読するだけの軽量な処理で、重い処理は持たない）。
  • タイムアウト時、Receptor はユーザーにループ停止の可否を確認し、ユーザーの指示に従う。選択肢：
    • ① 停止（作業を中止する）
    • ② もう少し待つ（そのまま続行し、再度様子を見る）
    • ③ 停止して再度トライ（直前の成功した段階から再開。確定済みの設計案や扱いかけのコードを活かし、最初からやり直さない）
  • タイムアウトが 2 回（N=2）に達したら、Receptor が強制停止し、結果を報告するのみ（以降はユーザーに確認しない）。
  • 自動判定でアクションを取ったとき（タイムアウトのリトライ、自動リトライ、強制停止など）は、その都度 Receptor 経由でユーザーに報告する（黙って自動処理しない）。
  • 判定は自発的：Receptor はユーザーの発言を待たずに停滞を監視し、slow/stuck を検知したら 自分から ①②③ の選択肢を投稿する。監視はチャットの状態ポーリング駆動のため、 アプリ閉鎖中は自然に休止し、再オープンで再開する（§5 の方針どおり）。
  • 判定基準は「無音時間」（総経過時間ではない）：総時間はプロジェクトの規模・難易度や 健全な差し戻しループで正当に伸びるため、固定の総時間では誤判定する。パイプラインの各進捗報告を ハートビートとし、「最後の生存信号から一定時間無音」のときだけ停滞と判定する （動き続けている限り、何周しても停滞扱いにならない）。判定時はそのときの工程・最後の動き・無音秒数を チャットに明示してユーザーに可視化する。

※ これらは1 作業（task_id）内の制御。短時間に実行が集中したときに自動で一時停止する安全装置（runaway guard）とは別レイヤ。

能力 ↔ 時間のトレードオフ： 高能力モデル（PRO）はフルアプリ生成に数分かかるのが正常で、 検証・レビューのゲートも時間を足す。よってタイムアウトの目安・LLM 読取上限は実態に合わせて長めに取り、 短く打ち切らない。良い結果を待てるよう、停止判断はユーザー（②もう少し待つ）に委ねる。

失敗（エラー）時の経路

  • コード生成やデプロイが失敗（report status=failed）したら、Orchestrator は短い自動リトライを行う（暫定 1〜2 回）。
  • それでも失敗する場合は、Receptor 経由でユーザーに報告して停止する（中断）。
  • 失敗したのはプレビューなので、公開済みの版は影響を受けない。
  • これは実行時エラー（failed）の扱い。Tester／Reviewer の品質差し戻し（needs_revision＝自動回数で打ち切らない）とは別レイヤ。

並列実行とタスク管理

  • Orchestrator はユーザー（プロジェクト）単位で最大 3 つまで同時稼働（他ユーザーと枠を共有しない）。各作業は task_id で識別し、ステータスモニターに表示する。
  • 3 枠が埋まっているときの新規実行命令は待機キュー（FIFO）に入れる。空きが出たら先頭から割り当てる。Receptor は順番待ちであることをユーザーに伝える。
  • 同一ミニアプリ（同じ feature）への同時改変は禁止（ロック）。 すでに改変中の場合、その feature への新規依頼は、その作業の完了を待つ。
コード規約： Reviewer が判定の基準とする「このアプリの中で定めたコード規約」は コード規約（Reviewer 判定基準） で定義しています。

4. 共通の運用ルール

  • ワーカーは独立して動作する（互いの内部状態を直接共有しない）。
  • 連携は定められたルールに基づく「指示」と「報告」のみで行う。
  • メインチャットでユーザーと会話するのは Receptor のみ。
  • Orchestrator はデプロイ前に必ず Tester の動作検証と Reviewer のレビューを通す。
  • Orchestrator はユーザー（プロジェクト）単位で最大 3 並列。
  • 各ワーカーは不要時は休止する（非常駐）。
  • 各ワーカーはコンテキストを保存するファイルを持ち、再開時にそれを読んでコンテキストを理解する。
  • コンテキストは適宜コンパクト化する。
  • Receptor は軽い処理のみを受け持ち、可能な限りユーザーに早く回答する。
  • 透明性（重要）：内部情報はなるべく詳しくユーザーへフィードバックする。 進捗・判断・自動アクション（リトライ・強制停止等）・失敗理由・使用モデル・レビュー指摘などを、 Receptor 経由でユーザーへ詳しく伝える。黙って自動処理しない。

5. ワーカーのライフサイクルとステータス

ステータスは 活動中 / 待機中 / 停止中 の3種。各ワーカーは API で起動・停止し、 自分のステータス変化を自分で記録します。

ステータスの定義

  • 活動中 … 指示を受けて考えている／処理しているとき。
  • 待機中 … どこかからの指示やリプライを待っているとき。
  • 停止中 … セッションが止まっているとき。

記録と起動・停止の仕組み（API 駆動）

  • 各ワーカーはステータスを変更するタイミングで、自分のステータスを記録する（そのための記録 API を使う）。記録には使用中のモデル種別（FLASH/PRO・具体モデル名）も含める（ステータスモニターに表示する）。
  • 各ワーカーを起動・停止させる API を用意し、他のワーカーからの操作で自動的に起動・停止する。
  • 基本は待ち＋ウェイクアップは回収用：依頼を出した送り手は結果を待機中で待つ。万一誤って停止していたら、受け手が状態を確認して起動 API で起こしてから報告を送る（ポーリングはしない）。
  • 固着（クラッシュ）の回収： ステータス記録には最終更新時刻を含める。Receptor／ステータスモニターは「活動中だが一定時間更新が無い」worker を検出したら停止扱いにする（クラッシュで自分では停止を記録できないケースの回収）。これは §3(b) のタイムアウト判定と同じ仕組みに乗る。

ワーカー別の起動・停止トリガー

ワーカー起動トリガー活動中待機中停止トリガー
Receptor メインチャットが開いたとき ユーザーや各ワーカーからの指示を受けて考えているとき 指示やリプライを待っているとき このウェブアプリが閉じられたとき
Orchestrator Receptor から指示を受けたとき 考えたり処理しているとき／Reviewer などからの報告を受けて考えているとき 指示やリプライを待っているとき プレビューのデプロイが完了したとき（公開・有効化はユーザー承認後に Control Plane が行い、Orchestrator は関与しない）
Reviewer Orchestrator がレビューを依頼したとき レビューしているとき — レビューを返したとき
Tester Orchestrator が検証を依頼したとき 検証しているとき — 検証結果を返したとき
Specialist Worker 担当のミニアプリを起動したとき アプリ内の処理を行っているとき 指示を待っているとき ミニアプリ画面が非表示／閉じられ、行っていた処理が完了したとき
待機中とウェイクアップの関係： 依頼を出して結果を待つのは待機中（フローが厳密なので、何を待つか分かっており ポーリング不要）。停止は本来の待ち方ではない。万一、待っている送り手が誤って停止していた場合に備え、 受け手が報告前に状態を確認して起こす（ウェイクアップ）のがフォールバック（§7）。
アプリ閉鎖中の挙動： ビルド中にユーザーが Web アプリを閉じても（Receptor は停止）、 Orchestrator はバックグラウンドで作業を継続する（進捗・レビュー・結果は会話／ステータスに永続化）。 再オープン時に Receptor が rehydrate し、その間の進捗・レビュー・結果をまとめてユーザーへ報告する。 タイムアウト判定は閉鎖中は休止し、再開時に再開する。

7. ワーカー間プロトコル（MCP 的 API）

MCP 的な API を通じて、ワーカー同士が定まった形で「指示（request）」を投げ、 「報告（report）」を返します。通信プロトコルを API で固定することで、指示の過不足をなくし、 依頼の品質を保ち、受け手の作業精度を担保します。スキーマに合わない指示・報告は受け付けません。

指示（request）メッセージ

フィールド意味
task_id作業全体の相関 ID（同じ仕事に属する指示・報告を束ねる）。
message_idこの指示の一意 ID（報告はこれを参照して返す）。
from / to送信元／宛先のワーカー種別＋インスタンス（例 Orchestrator#1 → Reviewer）。
intent依頼の種類。例：plan / build / edit / review / operate。
payloadintent ごとの定型データ（JSON Schema 準拠）。
context_refs必要な文脈への最小ポインタ。本体は各ワーカーが Firestore から取得（rehydrate）。
deadline_secこの指示の想定所要時間（目安）。Receptor が停滞（タイムアウト）判定に使うヒントで、超過しても受け手は自動失効しない（停止可否はユーザーが選ぶ。§3(b)）。

報告（report）メッセージ

フィールド意味
task_id対応する作業の相関 ID。
in_reply_to応答対象の指示 message_id。
from / to報告元（=指示の受け手）／報告先（=指示の送り手）。
statusok / needs_revision（Reviewer の差し戻し）/ rejected（スキーマ不正等で着手せず）/ failed（実行時エラー）。
result成果物または成果への参照（スキーマ準拠）。
findingsReviewer の指摘一覧（needs_revision 時）。
errorrejected / failed の理由。
usage使用モデル・トークン等（監査用。worker_runs に記録）。

やり取りのルール

  • 通信は非同期。受け手は着手時にステータスを活動中へ変え、完了時に報告を書く。
  • 基本は「待ち」。 フローを厳密に定めるので、依頼を出した送り手は何を待つかが分かっており、結果を待つ（待機中）。 ポーリングで探し回る必要はない。
  • ウェイクアップはフォールバック（誤って停止した時の回収）。 受け手は報告を送る前に送り手の状態を確認し、 停止していれば起動 API で起こしてから送る。起こされた送り手は保存済みコンテキストを rehydrate し、 task_id ＋ in_reply_to で対応する指示を特定して再開する。
  • 指示・報告は必ずスキーマ検証。通らない指示は着手せず rejected を即返す。
  • 進捗報告（interim report）：長い作業の途中でも、受け手は節目ごとに進捗を送る（最終報告とは別の途中経過）。特に Orchestrator は Receptor へ随時送り、Receptor がユーザーへ伝える。

宛先解決（worker レジストリ）

  • to はワーカー種別（必要ならインスタンス、例 Orchestrator#2）。種別 → 稼働インスタンスの解決は Control Plane のワーカーレジストリが行う。
  • 宛先が停止中なら、起動 API で起こしてから配送する（§5）。起こされた側は context を rehydrate して受信。

intent 別スキーマ（概要）

各 intent の payload（指示）と result（報告）の主フィールド。詳細スキーマ（JSON Schema）は実装時に確定。

8. 機能区分

固定機能

※ 多くは現行実装に準拠（Control Plane）。ただし「巻き戻し」（版を戻す）と「変更履歴」は要実装。

機能内容現行実装
メインチャット 主要機能。Receptor が対応する。 /api/reception/*
ステータスモニター ワーカーリストの表示と、各ワーカーのステータス（活動中／待機中／停止中）の表示。あわせて各ワーカーが使用中のモデル種別（FLASH / PRO、および具体的なモデル名）も表示する。 GET /api/control-plane/monitor
変更履歴 「いつ・誰が・何を・なぜ」変えたかを時系列で表示（制作・改変・公開・巻き戻し・無効化など）。監査ログをユーザーが読める形で見せ、巻き戻し先の選択にも使える。DevOps の透明性の中核。 要実装（audit_logs をユーザー向けに整形・表示）
セッション終了 ワーカーをすべて停止する。実行中のバックグラウンド作業を止め、ロックされたチャットを解放する。 POST /api/control-plane/stop-all（monitor.stop_all）
巻き戻し メインチャットが行った直近の制作・改変を取り消し、改変前の状態に戻す（その改変を「なかったことにする」）。 分岐は考えない（直線的な履歴を、直前のものから順に取り消すだけ）。 公開ごとに保存した版を使い、直前の版を即時に再有効化する（LLM 不使用・決定的）。 要実装：公開ごとに版（スナップショット）を保存する版ストア＋直前版の再有効化（Control Plane・Orchestrator/LLM 不要）
初期化 全アプリデータを削除し、メインチャットのみの初期状態に戻す。対象は会話・タスク・work_plans・API/UI レジストリ・承認・監査ログ・生成ビュー・feature_states 等。開発専用（DEV ONLY）の破壊的操作。 POST /api/control-plane/reset（registry.reset_all）
「巻き戻し」と「初期化」は別物。巻き戻し＝メインの改変を1つ取り消し、直前の版へ戻す（分岐は扱わない・直線的）、 初期化＝全削除でゼロから（DEV 専用・不可逆）。

可変機能

機能内容
ミニアプリ メインチャットの指示により新作・改変される。アプリチャットを持ち、 ユーザーが直接操作できるほか、Specialist Worker からも操作できる。 Specialist Worker から操作するための API を持つ。 Specialist Worker は、そのミニアプリが編集しているデータや API を扱う。 ワーカーはアプリに 1 つが標準。アプリチャット欄の表示は柔軟： 機能単位のオン/オフは会話（「ワーカーチャット不要」等）で即時切替、 画面単位の表示/非表示はアプリが AF.setChatVisible() で制御できる （いずれもワーカー自体は付いたまま）。
アプリチャット アプリの中のデータ処理や API 操作を受け持つ。 アプリごとに Specialist Worker を作り、アプリチャットからの指示を受けて そのアプリ内に限って作業を行う。 構造変更（新機能・項目追加など）は担当外。頼まれたら Specialist Worker が検知し、 メインチャット（Receptor → Orchestrator）へ取り次ぐ（ユーザーは境界を意識しなくてよい）。

9. コンテキストの保存と再開

ワーカーは非常駐（不要時は休止）なので、文脈はワーカー内に持たず Firestore に保存し、 起動のたびに最小限を読み直します（rehydrate）。肥大化はコンパクト化で防ぎます。

項目方針
保存先ワーカー／作業ごとに Firestore に保存（会話は conversations、各実行は worker_runs、定義は worker_definitions）。大きな生成物は Cloud Storage に置き参照のみ保持。
保存する中身直近の対話、判断ログ、現在の作業状態（task_id・段階）、整理済み要約、ユーザー設定／好み。
再開（rehydrate）起動時に context_refs（最小ポインタ）から必要分だけ読み直す。毎回フルロードしない。
コンパクト化対話・ログが閾値（件数/トークン）を超えたら、古い生ログを要約に畳んで生ログを破棄する。要約は更新・維持する。
ミニアプリの版公開のたびに版（HTML・設定のスナップショット）を保存し、巻き戻しの土台にする（直線的・分岐なし）。大きな HTML は Cloud Storage、ポインタを Firestore。
実装の先行例：ミニアプリの Specialist Worker は毎ターン「整理済み要約（organized summary）」を維持・更新している（backend/app/generated_app/task_worker.py）。これを全ワーカー共通のコンパクト化方式の雛形とする。

10. 権限と安全境界

  • ワーカーは自分の権限を増やせない。別ワーカーを勝手に作れない（Specialist Worker の設定は Orchestrator の定められた役割の範囲内でのみ行う）。
  • Orchestrator はデプロイはするが、Secret を読まない・IAM を触らない。副作用操作はすべて Tool Gateway 経由、出力はスキーマ検証。
  • Reviewer は判定（読み取り）のみ。コードの書き換えやデプロイはしない。
  • Tester は生成物を本番相当の Docker エミュレータ環境（モデルのみ claude、他は本番同等）で実行して検証するのみ。コードの書き換えやデプロイはしない（判定を返すだけ）。
  • Specialist Worker は担当ミニアプリ内に限定。他アプリのデータ・他ワーカーの領域に触れない。ミニアプリ本体はサンドボックス（iframe・外部通信／localStorage 遮断、保存は AF.load/save 経由）。
  • アプリ全体の利用は許可メール（ALLOWED_EMAILS ／ 管理者 allowlist）で制御（backend/app/auth.py）。

11. モデル割当（コスト方針）

「理解・軽い処理＝小型（FLASH）／重いコード生成＝上位（PRO）」を基本とします。 FLASH / PRO の階層はプロバイダによらず共通で、各環境のモデルにマッピングします。

プロバイダ（環境別）

開発・デモでは claude CLI のセッションを用い、本番では Gemini を使う。

環境プロバイダFLASHPRO
開発 / デモ claude CLI セッション（ホストブリッジ経由） CLAUDE_FLASH_MODEL（haiku） CLAUDE_PRO_MODEL（opus）
本番（Cloud Run） Gemini GEMINI_FLASH_MODEL GEMINI_PRO_MODEL

※ 開発でローカルの claude セッションを使うのは Gemini API コストの節約のため。ステータスモニターには、その時々の実モデル名が表示される（§8）。

ティアは能力帯で揃える。各プロバイダの同等モデルに対応させる（FLASH＝軽量、PRO＝最上位）。

Tier（能力帯）ClaudeGemini
FLASH（軽量・高速）haiku（claude-haiku-4-5）Gemini Flash（gemini-flash-latest）
PRO（最上位）opus（claude-opus-4-8）Gemini Pro（gemini-pro-latest）
PRO の正準は Opus ↔ Gemini Pro（同等の最上位）。Sonnet ではない。 開発・デモも CLAUDE_PRO_MODEL=opus を既定とする（能力帯を本番と揃え、生成品質を担保するため）。 Opus はフルアプリ生成が遅いが、タイムアウトは十分に長く（600s）、停止はユーザーが選べる（②もう少し待つ）。 どうしても速度を優先したい場合のみ一時的に sonnet へ下げる選択肢はあるが、既定にはしない。

ワーカー / タスクTier

Orchestrator（分類・計画立案）FLASH
Orchestrator（コード生成：HTML/API）PRO

現状、コード生成経路は PRO 呼び出しを 2 回行っている（計画再生成＋本生成）。Orchestrator の正式ワーカー化に合わせ、PRO 呼び出しは本生成 1 回に集約する（速度・コスト改善）。

9. DevOps / CI-CD

「まわす・とどける」。本作には2 つのデリバリーがあります： ①AgentForge 本体のデプロイ（人間が実施）と、②生成ミニアプリのデリバリー（AI ワーカーが毎回まわす DevOps サイクルそのもの）。

① 本体のデプロイ（現状）

対象手順状態
backend（core-api）gcloud run deploy --source（内部で Cloud Build / Artifact Registry を使用）。本番制約と手順は DEPLOY.md✅ 手動（検証済み手順）
frontendnpm run build → firebase deploy --only hosting。Firebase CLI が認証できない場合は DEPLOY.md の REST API 手順✅ 手動
push 起点の CI/CD（GitHub → Cloud Build → Cloud Run）トリガー設定で自動化⬜ 計画（MIGRATION）
方針：本番反映は、全フェーズをテスト環境（Docker：pytest＋本番相当エミュレータ実走）で確認してから一括で行う。 Cloud Run backend と Firebase Hosting frontend は別デプロイで、両方更新して本番反映完了。審査期間（〜7/24）は提出 URL を落とさない。 問題時は Cloud Run のリビジョン切替または Hosting release rollback で戻す。詳細は DEPLOY.md。

② 生成ミニアプリのデリバリー（AI が毎回まわす本作の核）

生成機能は view_manifest（完結 HTML＋操作ツール）方式のため再ビルド不要・即デリバリー。 そのかわり公開前に必ず品質ゲートを通します。

段階内容
生成Orchestrator（PRO）。改変は差分パッチ優先・失敗は自動リトライ・要求台帳を維持
検証ゲートTester（受け入れ条件ごと✅/❌）＋Reviewer（規約・設計適合）を並列実行。NG は差し戻し
プレビュー未公開のまま確認・修正指示で何度でも磨ける。未完成（stub）は公開不可
公開人間の承認「反映して」→ Control Plane が有効化＋版スナップショット保存
運用変更履歴・ステータスモニター（状態/待機理由/使用モデル）・監査ログ
ロールバック「戻して」で直前版へ即時復元（LLM 不使用・決定的・分岐なし）

状態の段階（生成機能）

confirm（受付確認） → plan（設計案） → built（プレビュー） → active（公開） → 版スタックで rollback ／ deleted（完全削除）。 rollback はデータ保持・可逆。一方で、ユーザーがアプリ削除を明示した場合は、 対象確認後にアプリに紐づくデータも完全削除する。状態を残す削除は再作成・schema 変更時のエラー源になるため実装しない。

テスト（まわす）

  • 自動：Docker 上の pytest（65+ tests・手順は ENVIRONMENT.md §2(C)）。
  • 実走：本番相当エミュレータ（compose：backend＋Firestore エミュレータ・モデルのみ claude）でパイプラインを実際に走らせて検証。

コスト・暴走対策

  • runaway guard（短時間の実行集中を自動一時停止）／差し戻しはタイムアウト制御（ユーザー判断・N=2 強制停止）
  • Cloud Run は min=0（scale-to-zero）。開発の LLM は claude ブリッジで Gemini コスト 0
  • 生成失敗のリトライは1回・stub は公開拒否（無駄な公開・課金を防ぐ）

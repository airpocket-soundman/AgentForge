7. データ設計

このページは初期構想（参考資料）。 ワーカー・パイプライン・承認フロー・安全装置の 正本は 5b. ワーカー定義・運用ルール／5c. コード規約（到達点はリポジトリ直下の VISION.md）。 記述が食い違う場合は正本に従ってください。

Firestore（native mode）が Control Plane の DB。状態・registry・監査・文脈をドキュメントで管理し、ファイル実体は Cloud Storage に逃がします。

永続化 API（機能ごとに増える）

動的 UI に置いた編集可能な要素（チェックボックス・テキストメモ欄・入力フォーム等）は、表示しただけでは保存されない。ユーザーが書き換えた状態をサーバに残すには、その要素に対応する永続化 API（読み書きエンドポイント）が必要になる。

したがって、機能を追加・拡張するたびに、その機能のデータモデルに対応する API 群（作成・取得・更新・部分更新・削除）を設計・生成・登録していく。UI が複雑になり編集要素が増えるほど、API も機能ごとに増えていく。これらは決定的 API（LLM 不使用・高速・確実）で、api_registry に登録し、generated-app-api が Firestore を読み書きして提供する。

図 7-1. 編集可能な UI 要素 → 永続化 API → Firestore。要素が増えるほど機能ごとに API が増える。

UI manifest は API にバインドする

UI の各コンポーネントは、どの API のどのフィールドを読み書きするかを view_manifest で宣言的に結びつける。

{
  "type": "checkbox", "label": "完了",
  "api": "task_update_api", "field": "done"
},
{
  "type": "textarea", "label": "メモ",
  "api": "note_update_api", "field": "body"
}

API 増殖を管理可能に保つ戦略

毎回ゼロから手書きせず、ハイブリッドにする。

  • ① 汎用 CRUD エンジン：entity（collection）とスキーマをパラメータ化した共通エンドポイントを基盤にし、新機能の単純な読み書きはこれで賄う（毎回 API を書かない）
  • ② 機能特化 API：特別なバリデーション・集計・副作用が要る所だけ、API Designer / Programmer ワーカーが専用 API を生成
  • いずれも api_registry に登録。要否（汎用で足りるか専用が要るか）は Orchestrator が判断
